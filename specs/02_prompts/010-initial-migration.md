## Task

[11] Create initial EF Core migration: generate and apply the first migration against a local dev
database.

## Spec

Tasks [3]–[10] each verified their schema by generating a throwaway migration, reading the emitted
SQL, and deleting it again. This task creates the one that stays, and applies it to
`dwelloot_dev` for the first time.

Three things must land before the migration is generated, because each is free now and costs a
follow-up migration afterwards.

### 1. `CompetitionClaim` — per-user loot box opening

Decided in review. Task [10] left "nothing records that a loot box has been opened" as an open
question, and the obvious fix — a single `opened_at` on `competitions` — is wrong given the
confirmed win-win behaviour: both partners open a box, so whoever opened second would find the
reveal already consumed. Signature moment of the app, silently broken for exactly the outcome that
is supposed to feel best.

`API/Entities/CompetitionClaim.cs`, `competition_claims(id, *competition_id, *user_id, opened_at)`:

- **Unique index on `(competition_id, user_id)`** — a partner claims a given box once. Same
  category as the `user_badges` uniqueness rule, and it makes `POST .../open-box` idempotent at
  the storage layer as well as in code.
- `CompetitionId` → **Cascade**: a claim is meaningless without its competition, and competitions
  already cascade from households, so restricting here would break household deletion.
- `UserId` → **Restrict**, consistent with every other user FK.

Row counts by outcome: a win produces one row, a win-win two, a voided period none.

This also makes the deferred "roll independently per partner" idea cheap: move `coins_awarded` and
`bonus_reward_id` from `competitions` onto this table. That is an additive change rather than a
restructuring, which is the main reason it beat the three-column alternative on `competitions`.

`relational-model.md` currently states loot-box claims are "not modeled as a separate table for
v1". That line is now wrong and gets updated rather than left contradicting the schema.

### 2. Fix the `badges` identity sequence

Flagged in log `008`. `HasData` inserts explicit ids 1–6 into a `GENERATED BY DEFAULT AS IDENTITY`
column without advancing the sequence, which still starts at 1 — so the first runtime insert would
collide on the primary key.

Fixed at the model level with Npgsql's `HasIdentityOptions(startValue: …)` rather than raw
`ALTER SEQUENCE` SQL in the migration body, for two reasons: it survives the migration being
regenerated, and it derives the start value from the seed array's length so adding a seventh badge
cannot leave the two out of step.

### 3. Nothing else

No entity changes beyond `CompetitionClaim`. The nine application tables from [3]–[10] go in as
already verified.

### The migration itself

- `dotnet ef migrations add InitialCreate` — a real name, not the `__Verify…` throwaways.
- `dotnet ef database update` against local PostgreSQL. `dwelloot_dev` does not exist yet; EF
  creates it. (Confirmed earlier that authentication succeeds and the failure was `3D000`,
  database-does-not-exist, so this is the expected first-run path.)
- The migration and its model snapshot are committed. They are the first files under
  `API/Migrations/` that survive.
